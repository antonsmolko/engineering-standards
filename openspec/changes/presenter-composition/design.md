# Design

## Context

[Запрос #42](https://github.com/antonsmolko/engineering-standards/issues/42), [proposal](proposal.md). Согласовано владельцем в рабочем диалоге: обе формы presenter допустимы, смешанный случай решается композицией. Baseline — [Presentation Model](https://martinfowler.com/eaaDev/PresentationModel.html); чистые функции — выбранный здесь способ реализации, не обязательный API этого паттерна.

## Goals / Non-Goals

Один документ в standards-frontend, потому что принцип независим от UI-фреймворка. State manager, обязательный FSD/API именования, Svelte runtime и массовое принятие прежних drafts не входят в результат.

## Decisions

- Сохранить FRONTEND-ARCH-001, новый отдельный принцип получает FRONTEND-ARCH-002. Функции принимают явно переданные, уже валидированные данные и нужный контекст; возвращают значения без мутаций/скрытых зависимостей/эффектов. Валидация недоверенных данных и обработка ошибок сохраняются на границе приложения; presenter не объявляется validator.
- Связанные вычисления объединяются при общей работе/смысловой связи; независимые могут оставаться отдельными. Объединяющая функция вызывает частные, частные не знают о компоненте/агрегаторе. Одного размещения на экране недостаточно для группировки.
- Реактивность/эффекты находятся в UI/adapters. Документировать явные входы/результаты/применимость и исключение простых выражений; примеры иллюстративные, без обязательной фабрики/имён файлов/менеджера состояния.
- Сохранять proposed: одобрение подхода не подтверждает ещё не рассмотренную английскую ревизию. При недостигнутом content gate выпуск #26 остаётся заблокирован. Reviewer проверяет полный текст по существующему content-approval checklist.
- Добавить empty changeset по текущей политике первого unreleased набора без version preparation. Удалить только presenter-candidate-example.svelte, user.presenter.ts, user-v2.presenter.ts, with-presenter-example.svelte, with-presenter-example-v2.svelte.

## Risks / Trade-offs

Избыточное дробление → применять по проверяемости и связности; простые выражения могут оставаться в компоненте. Смена исходного плана → публично связать #42/#20/#41, сохранить исходные критерии #20; superseded planning не выдавать за выполненную работу.

## Migration Plan

Одна документальная правка; existing full check/actual packs/consumers и независимое review, затем owner review. Нет runtime change — RED и новые tests текста не нужны. На момент PR #41 запрос #42 был ограниченным исключением из прежнего порядка отложения frontend-набора. После пересмотра #45 общая задача #24 закрыта как not planned; будущие темы сохранены в [inventory](../../../docs/architecture/requirements-inventory.md#deferred-content) до конкретного use case.
