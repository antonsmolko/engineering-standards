# Design

## Context

Мотивация описана в [proposal.md](proposal.md). Состояние main после [PR #29](https://github.com/antonsmolko/engineering-standards/pull/29): в репозитории восемь workspaces, пять manifests стандартов, канонические и встроенные JSON-схемы, загрузчик каталогов CLI, две заглушки конфигов и интеграционные тесты каталогов. npm run check проверяет типы TypeScript-хелперов/скриптов, версии workspace-записей lockfile и локальные manifest.requires, затем запускает node:test. В main ещё нет настройки Changesets и проверочного CI. [#9](https://github.com/antonsmolko/engineering-standards/issues/9) закрыта после PR #29; невыполненное требование Changesets переносится в отдельный follow-up, указанный в tasks.md.

Основных specs в OpenSpec пока нет. Две specs этого change задают новый контракт продукта. Старые архитектурные документы и критерии GitHub описывают более широкий функционал: их нужно согласовать при переходе, а не считать автоматически изменёнными созданием этого плана.

## Goals / Non-Goals

**Goals:** реализовать [standards-packages](specs/standards-packages/spec.md) и [manual-consumer-adoption](specs/manual-consumer-adoption/spec.md), сократив текущую реализацию, сохранив полезные документы и проверив установленные артефакты.

**Non-Goals:** оркестрация версий/релизов, CI и публикация в этом change; renderer/resolver, новый каталог, конфиги, интеграция с конкретным AI или компиляция Markdown. Не меняем asc-admin и приватные материалы. Не принимаем черновики стандартов.

## Decisions

### 1. Единица распространения — обычный npm-пакет

Сохраняем текущие имена и пути:

| Область | npm-имя | Каталог |
| --- | --- | --- |
| Core | @antonsmolko/standards-core | packages/core |
| Frontend | @antonsmolko/standards-frontend | packages/domains/frontend |
| TypeScript | @antonsmolko/standards-typescript | packages/technologies/typescript |
| Svelte | @antonsmolko/standards-svelte | packages/technologies/svelte |
| Svelte SPA | @antonsmolko/standards-svelte-spa | packages/stacks/frontend/svelte-spa |

Используем [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/) и [поле files в package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#files). Базовый поддерживаемый пример npm scripts — [npm/cli smoke-tests](https://github.com/npm/cli/blob/latest/smoke-tests/package.json). Сохраняем private root, Node 26 и текущие независимые версии пакетов. Документы читаются с диска, а не импортируются как исполняемые модули; доступ к метаданным package.json сохраняется, exports удалённых схем/manifests убираются без нового export API.

Альтернативы — оставить восемь активных workspaces или ввести общий bundle. Обе не соответствуют согласованному выбору пяти пакетов. Отложенные CLI/config можно восстановить из Git; они не должны оставаться условием текущих тестов или выпуска.

### 2. README заменяет точку входа в каталог

Каждый README перечисляет стандарты пакета, описывает применимость и известные сочетания простым английским текстом. Сохраняем полезный Markdown, стабильные пути документов и ID требований как текстовые метки. До удаления manifests переносим статус proposed в видимые пометки черновика там, где это необходимо; автоматического принятия нет. Ссылки внутри пакета относительные. Для другого пакета указываем его имя и README, не создавая относительный путь за пределы установленного пакета.

Из активной реализации удаляем пять manifest.json, схемы catalog/project из core, встроенные схемы и деревья отложенных tooling-пакетов. Полезные Markdown-шаблоны сохраняем, если они описаны или на них есть ссылки: шаблон не является runtime-схемой. Тесты и зависимости только для каталогов удаляем после появления заменяющих проверок сохраняемого поведения документов. Целевое количество тестов не фиксируем.

Альтернатива — оставить JSON manifests только ради тестов. Тогда после удаления потребительского сценария сохранится второй источник перечня документов и совместимости.

### 3. Подключение — явное действие потребителя

Документируем установку через npm как devDependencies и пример:

```markdown
Read and apply the applicable approved standards in these installed packages:
- node_modules/@antonsmolko/standards-core/README.md
- node_modules/@antonsmolko/standards-typescript/README.md
Follow each README's links to its standards. Draft documents are not approved rules.
```

Это пример текста, который вручную копируют в AGENTS.md потребителя, а не сгенерированный файл и не гарантия автоматического перехода AI по ссылкам. Решения человека и существующий приоритет инструкций потребителя сохраняются. Пути README предполагают обычную npm-установку в node_modules; другие менеджеры/структуры в начальном примере не обещаются. Инструкция поясняет npm ci для checkout с lockfile и необходимость читать changelog при обновлении. Пока пакетов нет в registry, соответствующие команды явно отмечаются как примеры будущего использования; локальная проверка использует tarballs.

### 4. Проверки покрывают сохраняемый контракт документов

Корневой check должен проходить для пяти пакетов и проверять их согласованность. Проверки удалённых каталогов/tooling заменяются проверками сохраняемого контракта документов.

Проверяем реальные упакованные артефакты и их установку во внешний проект: все пять пакетов вместе и отдельный набор core/TypeScript. Установленные name/version соответствуют пакетам; README, лицензия, changelog и перечисленные документы доступны без workspace links или загрузчика каталогов. Локальные ссылки разрешаются внутри артефакта; ошибка называет пакет и путь. Служебные и приватные материалы не попадают в пакеты. Установка сохраняет инструкции и конфиги потребителя.

Конкретные механизмы проверки ссылок, установки и диагностики выбираются в PR реализации задач 2.3 и 3.2, исходя из этих критериев и существующих тестов.

### 5. Общий процесс завершения проекта остаётся отдельным

Единственный результат реализации здесь — работающее распространение пяти пакетов документов и ручное подключение. Штатный [Changesets](https://github.com/changesets/changesets/blob/main/docs/intro-to-using-changesets.md), CI и публикация — будущие отдельные OpenSpec changes со своими задачами, планами и приёмкой. Они остаются частью завершения инфраструктуры до существенного наполнения, но здесь не вводятся спекулятивные API версионирования, синхронизация manifests или движок release groups.

Сохраняем явное принятие содержания владельцем, проверку приватных материалов и одобрение публикации. Прежний минимум принятого содержания из core, TypeScript и Svelte SPA сохраняется до пересмотра владельцем; удаление manifests меняет хранение доказательств, а не условие выпуска. Основание — существующие записи принятия, а не synthetic fixtures. Автоматизация публикации и credentials определяются в будущих планах.

### 6. Язык планирования и публикуемых документов

Обсуждения, proposal, design, specs и tasks ведём на русском. Служебные заголовки/маркеры OpenSpec, команды, имена пакетов и идентификаторы сохраняем в ожидаемом формате. Публикуемые стандарты, README, примеры инструкций потребителя и диагностика остаются на английском.

Две языковые версии возможны позднее. Это направление развития, а не принятое требование: переводы, выбор языка и механизмы синхронизации сейчас не добавляются.

## Risks / Trade-offs

- Ручное подключение можно пропустить, а ссылки могут устареть → короткий копируемый пример и проверка установленных путей; автоматическое применение не обещаем.
- Удаление JSON exports ломает неопубликованных потребителей каталогов → явно отмечаем удаление, сохраняем Git-историю и адаптируем тесты до удаления; публичная обратная совместимость не заявляется.
- Статус черновика частично хранится в manifests → сохраняем метки в документах и существующих записях принятия до удаления метаданных.
- Markdown не проверяет семантическую совместимость → описываем ограничения; автоматизацию добавляем только при конкретной будущей потребности.
- Исторический roadmap может противоречить новому scope → обновляем активные design/plan/handoff и критерии задач отдельным проверяемым документальным этапом до runtime-удалений.

## Migration Plan

1. Независимо проверить эти артефакты и согласовать активный roadmap/scope задач небольшим документационным PR. Создание плана само по себе не редактирует GitHub и не заменяет разрешения merge.
2. Реализовать переход к пяти пакетам в новой ветке конкретной задачи от текущего main, с RED до изменения поведения. Сохранить черновики и полезные packaging/offline проверки, заменив проверки каталогов на результаты использования документов.
3. Выполнить полный check по [Node-политике репозитория](../../../docs/architecture/2026-10-11-session-handoff.md#проверки-и-рабочий-процесс), проверить пять tarballs и внешних потребителей; отдельно независимо проверить полный diff и согласованность документов/задач до заявления о завершении. Merge требует одобрения владельца.
4. Отдельно спланировать Changesets, затем CI/подготовку публикации; проверить инфраструктуру на тестовых документах до принятия реального содержания и явно одобренного выпуска. Реальных повышений версий и публикации при переходе нет.

Откат до публикации — проверенный revert коммитов перехода. Примеры инструкций применяются вручную; внешний потребитель автоматически не изменяется.
