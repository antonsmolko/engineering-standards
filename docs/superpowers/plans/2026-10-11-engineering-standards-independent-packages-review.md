# Ревью плана: Engineering Standards Independent Packages

Ревьюируемый план: [2026-10-11-engineering-standards-independent-packages.md](2026-10-11-engineering-standards-independent-packages.md).
Спецификация: [../specs/2026-10-11-engineering-standards-design.md](../specs/2026-10-11-engineering-standards-design.md).

План связный: Review Focus привязан к задачам, тесты идут перед реализацией,
границы публикации заданы чётко. Замечания ниже по важности.

## Критичные

1. **В 0.1.0 не окажется ни одного активного требования.**
   - Task 2 оставляет все новые тексты `proposed` «до содержательного ревью».
   - Resolver и renderer включают только `accepted`, поэтому `docs/engineering-standards.md` для настоящих пакетов будет пустым.
   - ESLint-конфиги из Task 4 тоже нельзя назвать утверждённым стандартом.
   - Критерии приёмки 1 и 4 из спецификации проверяются только на fixtures.
   - Нужен явный шаг: кто и как переводит требования в `accepted` (отдельная задача или PR). Либо в плане прямо сказано, что 0.1.0 — каркас без принятого содержимого.

2. **Конфиги линтера противоречат правилу «активны только accepted».**
   - Task 4 разрешает включать правила, пока требования `proposed`.
   - Добавить тест: каждое включённое правило сопоставлено с `accepted`-требованием либо помечено `tooling-only`, и это описано в README конфига.

3. **Task 5 перегружена.** В ней renderer, safe-path, managed-реестр, три команды, bin и транзакционный rollback.
   - Разбить минимум на три части: safe-path и managed, renderer, команды.
   - Откат упростить: писать во временные файлы, делать rename, manifest — последним. Тогда `check` увидит рассинхрон.
   - Одной проверки путей в preflight мало: возможен TOCTOU (подмена пути между проверкой и записью). Проверять `lstat` по компонентам пути в момент записи.
   - Добавить тест на регистронезависимую ФС (macOS).

4. **Правило про symlink конфликтует с реальными `node_modules`.**
   - При pnpm и в монорепозитории потребителя пакеты — symlink'и за пределами корня проекта.
   - Разделить политики: корень проекта и цели записи — никаких выходов наружу; корни пакетов, найденные node-резолвингом, допустимы, граница действует внутри пакета.
   - Сейчас Tasks 2 и 5 этого не различают.

5. **Не описано, как CLI находит установленные пакеты.** В Task 5 сказано «из установленного набора потребителя», механизма нет.
   - Решение: `createRequire(root/package.json)` и `resolve('<pkg>/manifest.json')`, сверка найденной версии с `selection.packages`, понятная ошибка при отсутствии пакета.
   - `exports` каждого пакета спецификаций должен отдавать `manifest.json` и `package.json`. Добавить в тест Task 1.

6. **Нет пространства имён для ID требований.**
   - «Глобальная уникальность ID» есть, формата ID нет. Нужен префикс, например `CORE-ARCH-001`, `SVELTE-RUNES-003`. Иначе при появлении Vue или backend начнутся коллизии.
   - ID профилей (`core`, `frontend`, `svelte`) тоже плоские. `Resolved` не говорит, какой пакет профиль принёс, а без этого нельзя проверить «несколько версий профиля».
   - Добавить в `Resolved` поле `source: { package, version }`.

## Существенные

7. **Двойной источник версий.** `manifest.requires[].range` и `peerDependencies` в `package.json` дублируют друг друга. Добавить тест на совпадение или генерировать одно из другого.

8. **CLI и схемы в core.**
   - Схемы лежат в `standards-core`, а CLI их валидирует: зависимость CLI от core — peer либо схемы встроены в CLI.
   - Не определено поведение старого CLI на манифесте `schemaVersion: 2`. Нужна диагностика «неподдерживаемая схема», а не падение.
   - Не указан JSON-Schema валидатор (ajv или ручной) — влияет на зависимости CLI.

9. **Контракты неполные.**
   - `entrypoints` — без структуры.
   - `exception.decision` — без формата (URL, путь или ID).
   - `selectionHash` — без канонизации (сортировка ключей, переводы строк).
   - Хэши файлов — без нормализации CRLF/LF.
   - Нет каталога стабильных кодов диагностик, хотя `Report.diagnostics` на них опирается.

10. **`publishConfig.access: "public"` нигде не упомянут.** Scoped-пакеты по умолчанию restricted. Добавить проверку в layout-тест Task 1. Туда же `engines` и тест на минимально поддерживаемом Node (сейчас зафиксирован только локальный 24.14, потребители, вероятно, на 22).

11. **Релизная механика самописная.**
    - `scripts/releases/{plan,validate}.js` повторяют Changesets (независимые версии в workspaces, теги по пакету).
    - Нужно обоснование, почему не Changesets (правило 0.x «breaking = minor» настраивается), либо переход на него.
    - В публикацию заложить npm provenance или trusted publishing.
    - В Task 7: `permissions: contents: read`, запрет `pull_request_target`, отсутствие секретов в PR-джобах.

12. **Нет dogfooding и защиты веток.**
    - В Task 7 есть `lint` и `format:check`, но не сказано, какой конфиг они используют. Нужен собственный ESLint/Prettier репозитория, желательно на своих же пакетах.
    - У публичного репозитория на Free есть branch protection и rulesets (в отличие от приватного asc-admin). Обязательный check реален: добавить настройку защиты ветки, `SECURITY.md`, `CONTRIBUTING.md`, `CODEOWNERS`.

## Содержание и процесс

13. **Самая трудоёмкая работа в плане — одна строка.** «Компактные тексты общих/frontend/TS/Svelte/stack требований» в Task 2 — основной вклад проекта.
    - Вынести в отдельные задачи по пакетам: инвентаризация правил из `asc-admin/CLAUDE.md`, классификация по осям, формулировка, rationale, способ проверки.
    - Завести таблицу соответствия «правило ASC → ID» для будущего PR подключения asc-admin.
    - Отдельно перечислить, что остаётся локальным: `prefer-guard`, `arrow-body-style`, FSD-алиасы и прочее ASC-специфичное.

14. **Язык нормативных текстов не решён.** `AGENTS.md` и README в новом репозитории английские, спецификация и план русские. Для публичного npm-пакета выбрать язык контента явно. Русский ограничивает аудиторию — зафиксировать как осознанное решение.

15. **Инфраструктура опережает содержание.** Восемь пакетов, release-механика и tarball-тесты строятся раньше, чем есть хоть одно принятое требование.
    - Рекомендуется вертикальный срез первым: core + typescript + svelte-spa с 3–5 принятыми требованиями, прогнанный через resolver → renderer → `check` на tarball-потребителе.
    - Остальное расширять после этого. Проблемы из пп. 4, 5, 6 вскроются дёшево.

16. **Мелочи.**
    - Tarball-тесты ставят eslint и prettier в fixture. Для детерминизма и офлайн-CI нужны закоммиченный lockfile fixture и кэш; сейчас это только в Task 4, а касается и Tasks 5–6.
    - Конфиги из Task 4 проверять на TypeScript 5: в asc-admin он закреплён на `^5` из-за `svelte-check`, peer-диапазон не должен его выбрасывать.
    - В `asc-admin/docs/superpowers/` остаются неотслеживаемые копии spec и plan, а канон уже закоммичен в `engineering-standards`. Удалить копии, чтобы не расходились.
    - Старый план `2026-10-11-engineering-standards.md` помечен устаревшим, но лежит рядом. Удалить или оставить только ссылку.

## Рекомендация

Перед стартом поправить пп. 1–6 прямо в плане: это правки контрактов и порядка
задач, кода они не требуют. Затем решить по п. 15, делать ли вертикальный срез
первым.
