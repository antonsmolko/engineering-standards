# Спецификация публичного набора стандартов разработки

Статус: исходная архитектура и исправленный план согласованы в PR #2.
После merge владелец возобновил разработку; принятие конкретных нормативных
текстов и разрешение публикации остаются отдельными условиями.

## Цель и границы

`engineering-standards` — публичный GitHub-репозиторий и версионируемый
набор независимо версионируемых npm-пакетов с требованиями к разработке, конфигурациями проверок и инструкциями
для людей и AI-агентов. Он позволяет накапливать инженерные решения и применять
их в разных проектах без ручного копирования и расхождения правил.

Первый потребитель — `asc-admin`. Требования к продукту ASC, его авторизации,
данным сотрудников и API остаются в `asc-spec`. Универсальные стандарты
описывают, как разрабатывать программное обеспечение, а продуктовая
спецификация — что конкретно должно быть реализовано.

Согласованы публичность, разделение по применимости и начальный состав:
общие стандарты, frontend, TypeScript, Svelte и профиль Svelte SPA.
Также согласован каталог переиспользуемых спецификаций сложных модулей.
Каждый модуль проектируется отдельно; согласование каталога не утверждает
конкретную реализацию авторизации, API-клиента или менеджера состояний.
CLI и формат подключения ниже определяют предлагаемый контракт первой версии.

## Уровни требований

| Уровень                      | Ответственность                                        | Примеры                                                                |
| ---------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| `core`                       | Независимые от языка и платформы инженерные требования | Границы ответственности, критерии приёмки, ревью, безопасность, релизы |
| `domains/frontend`           | Особенности разработки клиентского интерфейса          | Доступность, состояния формы, браузерная навигация, адаптивность       |
| `technologies/typescript`    | Возможности и ограничения языка                        | Строгая типизация, проверка внешних данных, обработка ошибок           |
| `technologies/svelte`        | Особенности технологии                                 | Реактивность, вычисляемое состояние, lifecycle компонентов             |
| `stacks/frontend/svelte-spa` | Совместное применение технологий и инструментов        | TypeScript, Svelte 5, Vite, shadcn-svelte и архитектурный профиль FSD  |

TypeScript не относится исключительно к frontend: технологии и области
являются независимыми осями классификации. Специфичное правило нельзя
переносить в `core` только потому, что оно принято в первом проекте.

Svelte и Vue — технологии, а стек — их сочетание с языком, инструментами
и архитектурными решениями. Будущие правила Vue размещаются в
`technologies/vue`, а композиция Vue SPA — в `stacks/frontend/vue-spa`.

Архитектура относится к области применения требований, а не образует
отдельный универсальный пакет для всех платформ:

| Раздел                                     | Ответственность                                                                                     |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `core/architecture`                        | Общие принципы границ ответственности, явных зависимостей и публичных контрактов                    |
| `domains/frontend/architecture`            | Разделение UI и логики, владение состоянием и подготовка данных для представления                   |
| `domains/backend/architecture` — в будущем | Прикладные сервисы, транзакционные границы и инфраструктурные адаптеры                              |
| `technologies/svelte`                      | Реактивность, runes и lifecycle компонентов                                                         |
| `stacks/frontend/svelte-spa`               | Конкретная композиция технологий, слои FSD, расположение feature-моделей и соглашения об именовании |

Например, требование явных границ модулей относится к `core`, разделение
представления и логики — к frontend, а конкретные слои FSD и имена файлов
presenter — к профилю Svelte SPA. Подготовка сложных данных для шаблона
не требует отдельного presenter для каждого простого компонента.

## Структура репозитория

```text
engineering-standards/
├── packages/
│   ├── core/
│   │   ├── architecture/
│   │   ├── security/
│   │   └── workflow/
│   ├── domains/
│   │   └── frontend/
│   │       ├── architecture/
│   │       ├── accessibility/
│   │       └── forms/
│   ├── technologies/
│   │   ├── typescript/
│   │   └── svelte/
│   ├── stacks/
│   │   └── frontend/
│   │       └── svelte-spa/
│   └── tooling/
│       ├── eslint-config/
│       ├── prettier-config/
│       └── standards-cli/
├── tests/
│   ├── integration/
│   └── fixtures/
└── docs/
    └── architecture/
```

Иерархия каталогов отражает применимость стандартов. Она не связывает
версии пакетов: независимая публикация не требует плоского расположения.
Границы восьми начальных пакетов перечислены в разделе «Независимые пакеты
и конфигурации»; их корни содержат собственные `package.json`, changelog,
манифест, документацию, миграции и тесты по необходимости.

Вложенные `architecture`, `security`, `workflow`, `accessibility` и `forms`
являются разделами соответствующего пакета, а не отдельными npm-пакетами.
Группирующие `domains`, `technologies`, `stacks`, `stacks/frontend` и `tooling`
не публикуются. Корневой package.json приватный и управляет npm workspaces
с явным перечнем корней пакетов, а не с предположением `packages/*`.

`docs/architecture` описывает устройство самого `engineering-standards`:
границы пакетов, сборку профилей и релизы. Здесь не размещаются нормативные
правила архитектуры frontend или backend: они находятся в пакетах своей области.

Backend, Go, Vue и другие технологии и стеки добавляются отдельными изменениями
после проверки их требований. В первой версии нет пустых каталогов будущих
профилей или модулей. Будущие пакеты спецификаций модулей размещаются в
`packages/modules/<module>` после отдельного согласования.

Markdown содержит нормативные тексты. Машиночитаемые манифесты определяют
идентификаторы, применимость и связи требований. Конфигурации проверок
ссылаются на эти идентификаторы, но не становятся вторым источником текстов.

## Спецификации сложных модулей

`modules` — независимая ось организации: модуль описывает решаемую задачу,
а область и технология — условия применения. Каталог содержит спецификации
и архитектурные решения, не готовые runtime-библиотеки.

Общие архитектурные правила области остаются в `domains/frontend` или
будущем `domains/backend`. Спецификация сложного модуля, например
`modules/frontend-state`, уточняет эти правила для конкретной задачи и
ссылается на их ID, не копируя нормативные тексты. Модули, охватывающие
несколько областей, сохраняют общий контракт и отдельные варианты реализации
с явными ссылками на нужные области, технологии и стеки.

Спецификация модуля определяет назначение, границы ответственности,
интерфейсы, зависимости, модель данных, состояния и переходы. В ней описаны
жизненный цикл, обработка ошибок, отмена и конкуренция операций, требования
безопасности и сценарии приёмки. Неприменимость отдельного раздела указывается
явно, а не заполняется искусственным требованием.

Общие требования модуля не навязывают единственный технический вариант.
Каталог `decisions` описывает альтернативы и условия их выбора;
`implementations` содержит спецификации выбранных вариантов, их технологические
зависимости и критерии соответствия общему контракту. `acceptance` содержит
проверяемые сценарии, включая отказы и восстановление.

Первые кандидаты для отдельного проектирования:

| Модуль           | Общий контракт                                                               | Возможный вариант реализации                                   |
| ---------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `authentication` | Установление и завершение сессии, подтверждение личности, состояния и отказы | `browser-session` с явно выбранной политикой токенов и cookie  |
| `api-client`     | Проверка ответа, классификация ошибок, отмена и политика повторов            | `typescript-http` с выбранными HTTP-клиентом, схемами и Result |
| `frontend-state` | Владение состоянием, действия, вычисления и подготовка данных для UI         | `svelte-store-presenter` на Svelte runes                       |

Спецификация состояния различает области жизни: приложение, сессия, feature
и экземпляр страницы. Общий менеджер не означает единый глобальный store
для всех данных. Presenter отвечает за подготовку данных для представления,
не выполняет HTTP-запросы и не становится владельцем бизнес-состояния.

Позже добавляется `authorization` — спецификация контроля доступа, включая
ролевую модель. Она отделена от `authentication`: установление личности
не определяет разрешённые действия. Вариант `rbac` будет описывать роли,
permissions, назначения и правила вычисления доступа. Иерархия ролей,
ограничения по ресурсам, исключения и другие расширения согласуются отдельно,
а не считаются обязательными заранее. Имена ролей и permissions конкретного
продукта остаются в его спецификации.

Модули и варианты реализации ссылаются на общие требования по ID. Они могут
явно зависеть друг от друга: например, вариант браузерного API-клиента —
от контракта сессии. Не допускаются скрытые зависимости или копии требований.
Будущие модули перечисляются в roadmap без пустых спецификаций и не входят
в обязательную приёмку первого релиза.

## Формат требования

У каждого требования есть стабильный уникальный ID, заголовок, нормативный
текст, обоснование, область применения и способ проверки. ID не меняется
при перемещении документа и не используется повторно после удаления правила.

Раздельно указываются:

- уровень обязательности: `required` или `recommended`;
- состояние: `proposed`, `accepted` или `deprecated`;
- проверка: автоматическая, ручное ревью или комбинированная;
- связи: зависимости, уточняемые требования и заменяемые требования.

В обязательные проверки входят только применимые принятые требования.
Предложения доступны в документации, но не включаются как обязательные
в конфигурации и генерируемые инструкции. Устаревающие требования содержат
описание замены и условия перехода.

Пример: требование о сохранении черновика при ошибке запроса относится к
frontend. Его проверяют тестами поведения формы. Требование применять
`$derived` для вычисляемого состояния относится к Svelte и имеет отдельный ID.

## Сборка профиля проекта

Проект выбирает профиль в отслеживаемом файле `engineering-standards.json`.
Профиль стека перечисляет зависимости от области, технологий и `core`.
Сборка обходит зависимости, исключает дубликаты и формирует стабильный
порядок требований. Циклы, неизвестные ID и неизвестные профили — ошибки.

Проект также может выбрать модули и варианты реализации. Манифест варианта
перечисляет совместимые технологии и необходимые модули. Например,
`frontend-state/svelte-store-presenter` требует Svelte; выбор несовместимого
стека или отсутствующей обязательной зависимости останавливает `check`.
Выбор модуля не подключает его автоматически ко всем проектам этого стека.
Принятые требования выбранного модуля включаются в собранные инструкции;
невыбранные и ещё не принятые варианты не становятся обязательными.

Более специфичный профиль может уточнять общий, но не отменяет его молча.
Противоречие устраняется в стандартах или оформляется как явное исключение
проекта. В первой версии непротиворечивость текстов проверяется ревью;
CLI проверяет только формальные связи и заявленные конфликты.

Исключение содержит ID требования, причину и ссылку на проектное решение.
`check` показывает активные исключения. Исключение без причины или для
неизвестного требования останавливает проверку. Локальные продуктовые правила
не подменяют универсальные требования и остаются в документации проекта.

## Независимые пакеты и конфигурации

Репозиторий публикует независимые пакеты под scope `@antonsmolko`.
Единого пакета и общей версии для всего репозитория нет.

| Пакет                  | Каталог                               | Содержимое                                              |
| ---------------------- | ------------------------------------- | ------------------------------------------------------- |
| `standards-core`       | `packages/core`                       | Общие требования, формат манифестов, шаблоны            |
| `standards-frontend`   | `packages/domains/frontend`           | Frontend-требования, включая архитектуру области        |
| `standards-typescript` | `packages/technologies/typescript`    | Требования языка TypeScript                             |
| `standards-svelte`     | `packages/technologies/svelte`        | Требования технологии Svelte                            |
| `standards-svelte-spa` | `packages/stacks/frontend/svelte-spa` | Композиция профилей выбранного стека                    |
| `eslint-config`        | `packages/tooling/eslint-config`      | Исполняемые ESLint-конфигурации с отдельными экспортами |
| `prettier-config`      | `packages/tooling/prettier-config`    | Исполняемые настройки форматирования                    |
| `standards-cli`        | `packages/tooling/standards-cli`      | Проверка, сборка инструкций и их безопасное обновление  |

Название каталога и npm-имя независимы: например,
`packages/domains/frontend` публикуется как `@antonsmolko/standards-frontend`.
Перемещение пакета не меняет его публичное имя или стабильные ID требований.

Пакеты спецификаций не зависят от ESLint, Prettier или CLI.
CLI не устанавливает все профили транзитивно: проект выбирает и устанавливает
их явно. Документация остаётся применимой и без Node.js.

Доступность имён и право публикации проверяются перед созданием проекта;
при недоступности выбираются новые имена с владельцем, без автоматической замены.
Предлагаемая лицензия собственных материалов и кода — MIT; её принятие входит
в согласование этой спецификации. Сторонние материалы сохраняют свои лицензии.

Будущие модули публикуются отдельными пакетами: `spec-authentication`,
`spec-api-client`, `spec-frontend-state`, `spec-authorization`. Их варианты
реализации сначала находятся внутри соответствующего пакета спецификации.
Отдельный пакет варианта создаётся только при необходимости собственного
цикла релизов. Готовые runtime-библиотеки не смешиваются со спецификациями.

Конфигурации применяются явными импортами из пакета. Их экспорты и диапазоны
поддерживаемых инструментов составляют публичный контракт. Зависимости
проверок указываются как peer dependencies там, где требуется согласованная
версия с проектом. Версии тестируются на минимальных fixture-проектах.

Пакет не включает прикладные guard, API-клиенты или runtime-код приложения.
Локальные ESLint-правила переносятся только после удаления предположений
об алиасах, структуре и бизнес-моделях конкретного потребителя. Привязки
предоставляются настройками профиля или остаются локально.

## Контракт CLI

- `init`: проверить профиль и совместимость, предложить конфигурацию проекта,
  создать управляемые инструкции. Существующие файлы не перезаписывать.
- `sync`: сформировать инструкции из установленной версии пакета и выбранного
  профиля; обновить только файлы, ранее созданные CLI и не изменённые вручную.
- `check`: без записи файлов проверить профиль, ссылки требований,
  совместимость, исключения и соответствие управляемых файлов ожидаемому
  содержимому. Результат пригоден для CI.

Для `init` и `sync` предусмотрен `--dry-run`, показывающий изменения без записи.
Реестр управляемых файлов хранит точные версии пакетов, выбранные профили и хэши
содержимого. При ручной правке такого файла CLI сообщает конфликт и
останавливается, а не стирает правку. Цели записи и entrypoints ограничены
корнем проекта; выход через `..` или symlink не допускается. Read-only
корни пакетов обнаруживаются Node-резолвингом относительно потребителя:
symlink на установленный пакет допустим, но документы внутри пакета
не выходят за его canonical realpath-корень.

Все ошибки возвращают ненулевой exit code и сообщение о причине и следующем
действии. В отчёты не попадают секреты, токены или содержимое `.env`.
CLI использует установленные пакеты, не получает правила из плавающей
ветки GitHub и не выполняет установку зависимостей или сетевое обновление.
Lifecycle-скрипты установки, меняющие проект, отсутствуют.

## Инструкции для агентов

CLI создаёт отслеживаемый файл `docs/engineering-standards.md` с применимыми
правилами, их ID и точными версиями участвующих пакетов. Он доступен агенту
до `npm ci` и отражает версии, принятые проектом, а не состояние основной
ветки репозитория стандартов. Manifest управляемых файлов хранит тот же
набор package name/version и версию генератора отдельно.

Проектные `AGENTS.md` и `CLAUDE.md` ссылаются на этот файл. CLI не переписывает
их произвольное содержимое: при первичном подключении предлагает явную ссылку,
которую владелец проекта добавляет после просмотра изменений. `check`
проверяет наличие ссылки в заявленных точках входа.

Общие инструкции не требуют Codex, Claude или определённого плагина.
Названия инструментов и способы подключения описываются в отдельных адаптерах
и проектных правилах. Если `asc-admin` требует Superpowers, это требование
остаётся в локальном профиле проекта, а не становится обязательным для всех
пользователей публичного пакета.

## Версии и публикация

Проекты фиксируют точные версии выбранных dev dependencies и lock-файл. Обновление пакетов,
изменение управляемых инструкций и миграция конфигураций проходят отдельным PR.
Каждый пакет имеет свою semver-версию, changelog и тег вида
`standards-svelte@0.1.0`. Пакет и его документация относятся к этому тегу.
Изменение спецификации авторизации не требует релиза ESLint-конфигурации.

Связи между пакетами указывают имя и допустимый semver-диапазон.
Проектный выбор и manifest фиксируют фактически используемые точные версии.
CLI проверяет совместимость выбранного набора; несовместимые версии,
отсутствующая зависимость и несколько версий одного профиля в наборе дают
отказ. CLI не выбирает автоматически новую совместимую версию и не выполняет
сетевую установку. Корневой агрегированный каталог строится для проверки,
но не становится отдельно версионируемым монолитным артефактом.

При релизе публикуются только изменённые пакеты и зависимые пакеты, которым
действительно требуется изменение диапазона совместимости. Связанные релизы
могут публиковаться одной согласованной группой, но сохраняют отдельные версии.
CI проверяет граф зависимостей, отсутствие ссылок на неопубликованные версии
за пределами группы и сборку потребителя из tarball-пакетов вне workspaces.

Изменение смысла обязательного требования, добавление нового обязательного
ограничения или несовместимое изменение конфигурации считается breaking change.
После 1.0 это major-релиз, в серии 0.x — следующий minor-релиз с миграцией.
Редакционные исправления без изменения смысла выпускаются как patch.

Публикация выполняется только после успешных проверок из одобренного релиза.
Токены и настройки личного окружения не включаются в пакет. До первой публичной
публикации материалы из приватных репозиториев проходят проверку на секреты,
продуктовые сведения и права распространения. Авторизованная публикация
настраивается отдельно и не подразумевается согласованием архитектуры.

## Проверки и критерии приёмки первой версии

1. Требования классифицированы по применимости и имеют проверяемые ID.
2. Выбранный профиль собирается детерминированно; тесты покрывают дубликаты,
   циклы, отсутствующие зависимости и неправильные исключения.
3. Содержимое каждого упакованного npm-артефакта проверяется, включая документацию,
   CLI, exports и отсутствие приватных данных.
4. Fixtures TypeScript и Svelte SPA действительно импортируют конфигурации,
   проходят положительные тесты и отклоняют нарушающие правила примеры.
5. `init`, `sync` и `check` проверены на чистом проекте, повторном запуске,
   ручной правке управляемого файла и попытке выхода за корень проекта.
6. Все ссылки и идентификаторы в собранных инструкциях разрешаются.
   Формат манифестов поддерживает выбор модулей и вариантов; тестовые fixtures
   проверяют зависимости, несовместимость и отсутствие невыбранных требований
   в результате. Fixtures не подменяют согласование настоящих спецификаций.
7. Независимый релиз одного пакета не меняет версии несвязанных пакетов;
   несовместимый набор версий отклоняется. Проверки выполняются на упакованных
   артефактах, не только через workspace-ссылки.
8. Подключение `asc-admin` оформлено отдельным PR после релиза нужных пакетов.
   Проверки проекта остаются успешными, а новые требования мигрируются явно.

## Порядок дальнейшей работы

### Дополнения по ревью плана

Первые нормативные тексты не становятся accepted автоматически после
создания пакета. Владелец проводит содержательное ревью формулировок,
обоснования, применимости и проверки; принятие фиксируется отдельным PR
или решением. Первый релиз требует минимум трёх active accepted требований
в реальном core/TypeScript/Svelte SPA наборе, а не только в fixtures.

Публичные нормативные тексты, README и CLI-диагностика предлагаются на
английском; рабочие дизайн, план и ревью могут оставаться русскими.
Поддержка нормативных переводов не входит в первый релиз.

ID требований имеют формат `<NAMESPACE>-<CATEGORY>-<NNN>` с pattern
`^[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*-[A-Z0-9]+-[0-9]{3}$`. Последние два токена —
однословная ASCII-категория без дефиса и трёхзначный номер; всё слева — полный
зарегистрированный namespace пакета. Ownership проверяется точным равенством,
не совпадением префикса: `SVELTE-SPA-ARCH-001` принадлежит только `SVELTE-SPA`,
а не `SVELTE`. Разбор не зависит от набора выбранных пакетов; существующие ID
сохраняются, например CORE-ARCH-001 и TS-TYPES-001. Profile IDs соответствуют
иерархии: core, domains/frontend, technologies/typescript,
technologies/svelte, stacks/frontend/svelte-spa. Собранные записи содержат
source package/version; версия CLI фиксируется отдельно. Пакеты экспортируют
manifest.json и package.json, обнаруживаются через createRequire от
package.json потребителя и сверяются с точными версиями выбора проекта.

Compatibility ranges профилей хранятся только в manifest.requires;
tooling peerDependencies задают совместимость инструментов, не дублируя
semantic graph профилей. CLI использует Ajv и встроенный проверяемый snapshot
схем; неизвестный schemaVersion даёт стабильную диагностическую ошибку.

Форматы entrypoints, decision-ссылок, канонизация selectionHash и LF-хэшей,
а также каталог диагностик зафиксированы в исправленном плане. Для файловой
записи предусмотрены staged files, manifest-last, backups/recovery и
повторная проверка компонентов пути. Это не обещает multi-file atomicity
и полной защиты от злонамеренного конкурентного изменения локальной ФС.

Каждое включённое lint-правило связано с accepted нормативным ID либо
помечено tooling-only с отдельным обоснованием. Node 22.13.0/24.14.0 и
TypeScript 5 проверяются на locked fixtures до заявления совместимости.
Офлайн-прогоны требуют явной подготовки cache, без скрытой установки по сети.

До расширения конфигураций и release automation проверяется вертикальный
срез реальных пакетов resolver -> renderer -> check из tarballs. Уже
созданные восемь package skeletons сохраняются; frontend/Svelte зависимости
профиля устанавливаются явно. Независимые версии/changelog управляются
Changesets, наши дополнительные проверки отвечают за semantic metadata.

План предусматривает dogfooding собственных конфигураций, CONTRIBUTING,
SECURITY, CODEOWNERS, read-only PR permissions без secrets и отдельное
согласование branch protection после зелёного verify. Trusted publishing
и provenance настраиваются только в отдельно одобренном publication этапе.

### Порядок продолжения после возобновления работы

Владелец явно возобновил работу после merge PR #2. Применяется исправленный план:
доработки существующего каталога, нормативное ревью и принятие требований,
resolver, managed-файлы, renderer и команды, затем реальный вертикальный
tarball-срез. Расширенные конфигурации и независимая release automation
следуют после этого среза. Подключение потребителей выполняется после
проверки и публикации одобренной группы артефактов, отдельно от рефакторинга
прикладного staff-модуля.

Соглашения store/presenter/UI, форм, API и ошибок из ревью `asc-admin` сначала
проходят отдельное архитектурное согласование. Они не считаются автоматически
утверждёнными содержимым этого публичного набора.
